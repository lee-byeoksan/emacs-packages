# abtop 기능 분석과 EAM 적용 후보

분석일: 2026-09-17. abtop main `4b96568666c1f3b887202d14b0a1c6171315e520` / Cargo 버전 0.5.5.
비교 대상: EAM `b7b0efc27c60204e926e18f396b04feb37ab2538`.

공개 저장소를 임시 디렉터리에 받아 README와 실제 수집기·표시·설정·요약 코드를 읽었다. abtop을 설치하거나 실행하지 않았으며, 실제 처리 성능·사용자 환경별 정확도는 측정하지 않았다. 아래 우선순위와 비용은 EAM에 대한 제안이다. 기능 구현 승인이나 확정 일정은 아니다.

## 결론

abtop의 가장 큰 가치는 여러 에이전트의 작업 진행 상황을 한 화면에서 비교하는 데 있다. EAM은 이미 CLI 실행·지속·재접속·입력 편집을 관리한다. 따라서 별도 대시보드를 추가하기보다 기존 `eam-sessions`와 `eam-status`의 관찰 기능을 보강하는 것이 적합하다.

우선 후보는 ① 목록의 작업 상태와 컨텍스트, ② 현재 요청·도구의 세션 상세, ③ 한도 데이터의 출처·갱신 시각·정확한 기간 표시다. 포크하거나 abtop 전체를 의존성으로 넣는 방향은 제안하지 않는다.

## EAM에 적용할 사용자 흐름

### 1. 어떤 세션으로 돌아가야 하는지 결정

세 개의 세션 중 하나는 응답 중이고 하나는 사용자의 확인을 기다리는 상황이다. 현재 EAM의 attached/detached는 연결 상태이므로 이 차이를 설명하지 못한다.

`eam-sessions`에 연결 상태와 별개의 작업 상태·컨텍스트 열을 추가하는 것이 좋다. 예를 들어 `attached | 도구 실행 | ctx 74% | NEW`다. 알림을 읽었는지와 AI가 무엇을 하는지도 별도다. 목록을 열었을 때만 제한적으로 갱신하고, 소유권 미확인 세션은 확정된 실행 상태처럼 표시하지 않는다.

주의: abtop의 상태는 도구 레코드·미응답 사용자 메시지·자식 프로세스 CPU 등에서 추론된다. CPU 활동만으로 생각 중인지, 단순 입력 대기인지, 승인 대기인지 확정할 수 없다. EAM에서는 명시적 이벤트를 우선하고, 불확실하면 `미확인` 또는 `추정`으로 표현한다.

근거: [Claude 상태 판별](https://github.com/graykode/abtop/blob/4b96568666c1f3b887202d14b0a1c6171315e520/src/collector/claude.rs#L591-L622).

### 2. 긴 응답 중 내가 무엇을 시켰는지 확인

`eam-status`에서 현재 연결된 대화 ID를 사용하여 최근 실제 사용자 요청, 진행 중 도구 이름, 도구의 경로/명령 일부, 마지막 이벤트 시각을 보여준다. 현재 요청은 마지막 user-role 레코드와 같다고 가정하지 않는다. 도구 결과·내부 메타 메시지를 제외해야 한다.

이 흐름에 대화 선택 창이나 AI 요약은 필요 없다. 최신 요청이 너무 길면 기본 미리보기 길이를 제한하고 명시적 동작으로 일반 버퍼에서 더 읽는다. transcript 자체를 EAM 저장소에 다시 복사하지 않는다. 사용자 프롬프트에 task 관련 문구가 있어도 과거 제거한 eam-task 기능을 부활시키는 것은 아니다.

### 3. 한도 또는 컨텍스트 때문에 중단될 가능성 확인

헤더의 기존 두 줄 구조는 유지한다. 한도/컨텍스트에 Emacs warning/error face를 적용하고 출처와 마지막 관측 시각을 상세에서 보여준다. 80%/95% 같은 값은 제안 임계치이며 사용자 설정으로 변경할 수 있어야 한다. 반복 데스크톱 알림은 기본으로 추가하지 않는다.

한도는 실제 window 길이로 표시한다. secondary를 언제나 주간이라고 가정하지 않는다. 새 조회가 실패하면 마지막 성공 값을 유지하되 `3분 전 · 갱신 실패` 등으로 상태를 분리한다. 과거 수치로 현재 한도를 단정하지 않는다.

abtop은 Codex token_count에 포함된 rate_limits를 읽는다. EAM에서도 이미 읽는 기록에 해당 데이터가 있다면 보조 자료로 사용할 수 있다. 다만 기록의 계정 식별이 현재 계정과 연결되지 않으면 현재 계정 한도로 승격하지 않는다. EAM의 기존 공식 계정 조회가 제공하는 누적/일별 토큰 정보는 별도의 가치가 있으므로 없애지 않는다.

근거: [Codex 한도 파싱](https://github.com/graykode/abtop/blob/4b96568666c1f3b887202d14b0a1c6171315e520/src/collector/codex.rs#L1385-L1442), [한도 화면](https://github.com/graykode/abtop/blob/4b96568666c1f3b887202d14b0a1c6171315e520/src/ui/quota.rs).

### 4. CLI가 끝났는데 개발 서버가 남아 있는 이유 확인

현재 세션의 자식 프로세스·포트를 `eam-status`에서 요청 시 조회한다. 세션 종료 뒤 남은 서버는 사용자가 계속 쓰려던 것일 수 있다. 종료 후보로 보여줄 수는 있지만 자동 정리하지 않는다.

abtop의 orphan 판별은 지속 관측에서 부모-자식 관계를 기억한다. 일회성 프로세스 조회만으로 동일한 정확도를 얻을 수 없다. EAM에서도 PID 재사용과 프로세스 시작 시각을 고려해야 하며, 먼저 조회 기능만 제공하는 것이 적합하다.

근거: [프로세스 수집](https://github.com/graykode/abtop/blob/4b96568666c1f3b887202d14b0a1c6171315e520/src/collector/process.rs), [snapshot의 orphan 제약](https://github.com/graykode/abtop/blob/4b96568666c1f3b887202d14b0a1c6171315e520/src/snapshot.rs).

## 데이터 수집에서 참고할 점

- 프로세스 스냅샷 공유: abtop은 한 tick의 ps/포트 결과를 여러 collector가 공유한다. EAM은 현재 세션별 usage worker와 quota cache를 사용한다. 세션 수가 늘 때 중복 조회를 줄일 여지가 있다. 단 계정 사용량 캐시를 provider 이름만으로 합치면 여러 계정이 섞이므로 인증 루트/계정 구분을 유지해야 한다.
- 증분 읽기: Claude 수집기는 마지막 offset 이후 추가분을 읽고 파일 교체·축소를 감지한다. EAM에서 현재 요청·도구 이벤트까지 늘릴 경우 참고 가치가 높다. 현재 EAM의 bounded head/tail 읽기와 비교해 측정한 뒤 도입해야 하며 무조건 더 빠르다고 단정하지 않는다.
- 제한된 기록: abtop에는 대화 미리보기 12개, 파일 작업 1,000개, 그래프 200 샘플 같은 제한이 있다. EAM도 장기 세션과 종료된 세션의 캐시 수거까지 포함한 한도를 유지해야 한다. abtop의 모든 맵이 고정 크기인 것은 아니다.
- 비용이 다른 조회 분리: 포트·파일 소유자 검색과 세션 표시 갱신을 같은 빈도로 실행하지 않는다. EAM의 terminal redraw 16ms와 메타데이터 조회 주기는 별개로 유지한다.
- 중복 합산 방지: abtop은 Codex 입력에서 캐시를 빼고 별도 항목으로 저장한다. EAM은 CLI 원본 input에 cache가 포함된 의미를 유지한다. 수치를 복사해 더하면 안 된다. token rate도 캐시 제외/포함과 시간 구간을 명확히 해야 한다.

## 그대로 가져오지 않을 부분

- AI 제목 생성: 일반 tick에서 요약 작업을 시작할 수 있고 claude --print에 별도 제목 생성 프롬프트를 보낸다. tick_no_summaries 경로는 이를 생략한다. EAM에는 사용자 이름 또는 원문 미리보기로 충분하다.
- 영구 설정 설치: abtop --setup은 Claude 설정과 statusline 스크립트를 기록하며 해당 스크립트는 python3를 사용한다. EAM의 Rust callback·실행 인수 한정 연결을 유지한다.
- 대시보드 전체 이식: EAM에서 제거한 시작 화면·workspace·task 관리 기능을 다시 넣을 근거가 되지 않는다. 기존 목록과 status에 기능을 배치한다.
- 휴리스틱의 사실화: 컨텍스트가 이전보다 30% 이상 줄면 압축으로 추정하는 로직과 모델별 컨텍스트 크기 fallback은 참고용이다. EAM에서는 공식 ctx 수치/명시적 압축 이벤트를 우선하고 추정치를 구별한다.
- raw snapshot 공유: abtop JSON은 transcript에서 파생한 대화/도구 미리보기 등을 포함한다. EAM에 이를 그대로 복제 저장하거나 외부 노출할 필요는 없다.

## Pro/Max 배수 등급에 대한 발견

검토한 account/rate-limit 모델·수집·표시 경로에서는 Codex Pro 5x/20x 또는 Claude Max 5x/20x를 자동 판별해서 표시하는 구현을 확인하지 못했다. abtop을 참고한다고 이 문제가 바로 해결되지는 않는다. 이것은 provider가 다른 경로에서도 배수를 제공하지 않는다는 증거는 아니다.

## 제안 순서와 검증 기준

| 순서 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1 | 세션 상세에 현재 요청·도구·관측 시각 | 같은 디렉터리의 동시 대화가 섞이지 않음. resume/clear 이후 ID 갱신. AI 호출 없음. 미확인 상태를 표시 |
| 2 | 목록의 작업 상태·ctx, 폭별 열 축소 | attached/detached와 분리. n/p와 C-M-n/p 계약 유지. detached 자동 attach 없음. 한글 이름·좁은 창 검증 |
| 3 | 한도 표시·캐시 개선 | 값 없음과 0 구분. 조회 실패·오래된 값 표시. 비주간 window 처리. 여러 인증 루트 격리 |
| 4 | 사용량 추이·파일 작업·선택적 Git 정보 | 샘플 수·읽기량 상한. 세션 종료 시 캐시 수거. 1/10/50 세션 부하 비교 |
| 5 | 프로세스·포트·서브에이전트 진단 | 소유권/추정 구분, 읽기 전용 시작. 임의 외부 세션에 제어권 부여하지 않음 |

상태 수집에 필요한 이벤트 신뢰도를 먼저 검증해야 한다. 그래프와 상태색을 먼저 붙여 정확하지 않은 정보를 더 그럴듯하게 만드는 순서는 피한다. GUI 검증은 실제 한글 입력·창 분할·스크롤과 키 전환을 포함하고 배치 parser 테스트와 별도로 기록한다.
